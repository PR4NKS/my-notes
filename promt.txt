## 2. Secure Admin Authentication

Create a secure administrator system for managing the notes website.

### Login Page
- Provide a dedicated admin login page.
- Allow access using an administrator password.
- Display clear validation errors for incorrect credentials.
- Add loading states and appropriate error handling.
- Do not expose private admin information to public visitors.

### Authentication Security
- Verify authentication on the backend for every protected operation.
- Hash passwords using an appropriate password-hashing algorithm such as Argon2id or bcrypt.
- Use secure sessions or properly implemented authentication tokens.
- Configure HTTP-only, Secure, and appropriate SameSite cookies when using cookie-based sessions.
- Implement login rate limiting and brute-force protection.
- Prevent session fixation and invalidate sessions on logout.
- Support configurable session expiration.
- Protect cookie-authenticated state-changing requests against CSRF.
- Never store administrator passwords in localStorage, frontend JavaScript, or source code.
- Never ship an initial production password in the repository.
- Provide a secure first-time administrator setup process.
- Allow the administrator to change the password after authentication.
- Ensure private admin APIs cannot be accessed by bypassing the frontend login screen.

### Admin Access Rules
Only authenticated administrators may:
- Upload notes and attachments.
- Create, edit, rename, move, publish, unpublish, or delete notes.
- Create, rename, move, or delete folders.
- Manage document metadata.
- Change administrative settings.

Public visitors may read and search published notes only.

## 4. Note Upload System

Implement a real upload system connected to the backend and persistent storage.

### Supported File Types
Support these formats where appropriate:
- Markdown: `.md`, `.markdown`
- Plain text: `.txt`
- PDF: `.pdf`
- Documents: `.docx`
- Images: `.png`, `.jpg`, `.jpeg`, `.webp`, `.gif`, and `.svg` only with appropriate security sanitization.

Additional formats may be supported if they fit the existing architecture.

### Upload Workflow
1. The administrator opens the upload interface.
2. Selects one or more files or drags them into the upload area.
3. The website validates file types and sizes.
4. The user chooses a destination folder.
5. The system extracts or processes supported content.
6. The administrator previews the imported note.
7. The administrator saves it as a draft or publishes it.
8. The note appears in the Explorer and becomes searchable according to its publication status.

### Upload Requirements
- Support multiple-file uploads.
- Show individual file progress and upload errors.
- Prevent duplicate imports where appropriate.
- Handle interrupted uploads and network failures gracefully.
- Sanitize filenames and avoid path traversal.
- Validate file signatures where applicable, not only file extensions.
- Configure sensible upload-size limits.
- Reject unsupported, malformed, or dangerous files.
- Avoid executing uploaded files.
- Prevent arbitrary filesystem access through user-controlled filenames.
- Store uploaded files outside executable or publicly exposed application directories where appropriate.
- Use safe file-serving headers and access controls.
- Ensure failed uploads do not create broken notes or orphaned attachments.

Never trust uploaded file content.

### Rendering Rules

- Preserve heading structure.
- Generate unique heading anchors.

- Resolve local image and attachment references correctly.
- Show a helpful message for missing attachments or broken note links.
- Sanitize rendered HTML and Markdown output.
- Prevent stored XSS through scripts, event handlers, unsafe URLs, and malicious embedded content.
- Disable unsafe raw HTML or sanitize it using a suitable established library.

Editing a note must update the persisted version, not merely the browser display.

## 11. Privacy, Access Control, and Security

Treat this as a real documentation platform containing potentially private security research.

- Separate public notes from private notes and drafts.
- Require server-side authorization for private content.
- Prevent unauthorized direct attachment downloads.
- Protect against SQL injection, path traversal, XSS, CSRF, and insecure direct object references.
- Validate note identifiers and request parameters.
- Rate-limit authentication and sensitive operations.
- Keep secrets in environment variables or a secure secret manager.
- Avoid logging passwords, session tokens, or sensitive note content.
- Provide safe error messages without leaking internal paths or stack traces.
- Add appropriate security headers.
- Restrict upload types and file sizes.
- Keep dependencies maintained and avoid unnecessary packages.
- Use HTTPS in production.

Publicly published notes may be readable without an account. Private notes and administration must remain protected.
